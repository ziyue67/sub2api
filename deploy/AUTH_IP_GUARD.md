# 网页认证 IP 防护

公开认证的凭证、注册及 OAuth 登录/建号入口默认启用以下防护；管理员建号和业务 API 不使用注册额度。刷新、登出、密码找回/重置和普通验证接口不经过新增守卫，OAuth 支付入口也不在其范围内。

| 行为 | 默认策略 |
| --- | --- |
| 邮箱或 OAuth 新建账号 | 同一 IPv4 / IPv6 /64 累计最多 2 个，跨实例共用 PostgreSQL 额度 |
| 网页密码登录、OAuth 绑定登录、2FA、passkey finish | 同一 IP 首次失败起 15 分钟内累计 10 次失败后，封禁认证入口 1 小时 |
| 封禁期间 | 受保护入口返回 HTTP 429 和 `Retry-After`，不执行后续认证；被拦截请求不延长封禁 |
| Redis 不可用 / 无法解析客户端 IP | 受保护入口拒绝请求，返回 HTTP 429；新增守卫不影响刷新和登出 |

仅累计服务端明确返回的 `INVALID_CREDENTIALS`、`TOTP_INVALID_CODE`、`PASSKEY_VERIFICATION_FAILED` 错误；错误 TOTP 虽为 HTTP 400 仍会计数。普通格式错误、验证码缺失、OAuth 会话过期、禁用账号或后台模式限制不累计，429 限流与 5xx 服务故障也不累计。不同登录方式共用失败计数；成功登录不清空失败历史。第 10 次失败保留原有错误响应，其后的请求返回 429；已经放行的并发请求可能继续完成。

刷新仍保留原先每分钟 30 次的独立限流及其 Redis 故障 fail-close 策略；本次只移除新增封禁对它的影响，不承诺 Redis 故障时仍能刷新。登出不访问新增封禁状态。

注册额度在所有公开认证请求的上下文中标记，在统一用户仓储中以原子 UPSERT 扣减，与用户写入及外层邀请码事务一同提交或回滚。不因重启或清理 Redis 丢失。删除账号不退额度，防止删号重领；账号创建已经提交后的后续 OAuth 绑定补偿删除也不退额度。达到上限返回 HTTP 403、`reason=REGISTRATION_IP_LIMIT`。已有账号登录不扣额度。

## 升级与可信代理

迁移 `285_registration_ip_quotas.sql` 自动创建独立额度表，不修改历史用户。历史账号没有可靠的注册 IP，不能从最近登录 IP 推断，因此不追溯额度，从升级后开始累计。

迁移 `286_registration_ip_quota_created_at.sql` 添加 `created_at`，已有额度行记录的是迁移时间，不能作为历史注册时间；该字段仅用于排障，不用于清理或返还额度。

这两项防护使用 `GetTrustedClientIP`，只通过 Gin 的 `server.trusted_proxies` 信任链（或已有验证的转发 IP）获取地址，忽略兼容模式对原始 `CF-Connecting-IP`、`X-Real-IP`、`X-Forwarded-For` 的直接信任。IPv4 和 IPv4-mapped IPv6 共用单地址键，原生 IPv6 规范化为 `/64` 网段再计算 SHA-256。

未配置 `server.trusted_proxies` 时，默认仅信任 `127.0.0.1/32` 和 `::1/128`，适用于本机 Nginx / 1Panel 反代；这意味着本机进程也处于可信代理边界内。显式配置列表会替换默认值，显式 `[]` 或空的 `SERVER_TRUSTED_PROXIES` 环境变量禁用代理信任；非法列表仍禁用信任，不回退默认值。Docker 桥接、私网或远程反代必须显式列出实际代理地址/受控网段，不会自动信任全部私网。修改需重启应用。反代应覆盖 `X-Real-IP`，覆盖 `X-Forwarded-For` 或在末尾追加真实对端；程序从右向左解析可信代理链，不采用攻击者放在链首的地址，也不直接信任 `CF-Connecting-IP`。不要信任任意来源或允许客户端绕过反代访问源站。

配置错误可能把所有用户算到同一代理 IP。未配置或代理信任不可用时，收到转发头且解析仍停留于 TCP 对端的首次请求会输出 WARN，日志不打印头值或来源 IP。排查时通过手机移动网络产生新请求：客户端 IP 应显示公网来源，TCP 对端保留 `127.0.0.1` 是正常的；历史访问记录和注册额度不自动重写，正确识别后的新来源使用自己的额度，不要清空全表。显式空列表的旧部署需主动改为实际代理列表才能恢复转发 IP 解析。

共享公网出口或同一 IPv6 /64 下多个用户共用两个注册名额，管理员可通过后台代建账号。跨 IPv4 或不同 IPv6 /64 的分布式攻击仍需要验证码、邀请制或边缘防护。若曾部署此 PR 最初的单地址 IPv6 实现，旧的地址哈希无法恢复成 /64，升级时该部分额度/临时封禁不迁移；IPv4 键保持一致。避免新旧实例混跑。

## 状态与解除封禁

新表仅保存规范化 IP 的 SHA-256 和累计账号数，无原始 IP、邮箱或密码。哈希用于避免直接记录 IP，并非匿名化承诺。此防护不新增用户凭据日志，也不内置任何事件中的真实 IP。

Redis 键为 `auth_abuse:{<来源 SHA-256>}:failures` 和 `auth_abuse:{<来源 SHA-256>}:banned`，分别带 15 分钟和 1 小时 TTL。正常到期自动解除。异常无 TTL 的封禁键会按 fail-safe 补为完整一小时；正常封禁不续期。管理员确认误封时，可计算目标 IPv4 地址或 IPv6 /64 的规范化哈希，仅删除这两个对应键；不要清空 Redis。Redis 状态被清理或 Redis 无持久化重启会清除临时封禁，因此仍应保留边缘/fail2ban 防护。

回滚二进制不会删除额度表，可保留以便重新升级；旧二进制不会继续统计。跨新旧版本灰度期间，旧实例建号不受新额度约束，因此应一并升级公开认证实例。此次变更不包含 SSH、系统防火墙、发布或生产部署操作。
