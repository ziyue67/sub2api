# 优先调度

入口：**智能运维 → 优先调度**（`/admin/priority-scheduling`）。默认关闭。设置保存在 `priority_scheduling_v1`，无需数据库迁移。

## 生效范围

作用于 OpenAI 文本请求的自由选路，包括接入统一 OpenAI 调度器的兼容通道。可按分组 ID、请求模型名精确限定范围，留空表示不限。图片、视频及其他平台不启用此策略。

开启后，命中范围的请求使用高级调度器，优先利用较空闲的真实容量，容量接近时再按体验、优先级和权重分流。历史统计未就绪也继续均衡，不恢复固定 Top-K。关闭优先调度后恢复原调度开关控制。硬会话绑定、不可迁移的 previous_response_id、模型权限、账号状态、分组利润门槛、compact 能力、订阅优先分池和最终并发槽校验仍生效。**候选评分不是最终选择记录**；软粘性加分不参与本策略评分。

“在兼容的 BPS 与原生账号间均衡分流”对应 balance_protocols，默认开启；旧设置缺该字段时也使用此默认值，旧客户端保存时省略字段会保留当前值。开启后，不再仅因 BPS 池还有一个槽位就长期排除空闲的原生候选。仍按每个账号自身的协议发送，不自动开启 BPS，也不放开账号或分组模型限制。关闭此项可恢复 BPS 优先、原生兜底；图片、视频及不匹配优先调度范围的请求不受影响。

优先调度开启时，可迁移会话若存在利用率至少低 20 个百分点、每绑定分组的可用容量权重大于原账号两倍的兼容账号，可临时返回自由选号；保留原会话绑定，不迁移已发送请求，不改写已有响应或任务归属。健康且负载接近的会话继续复用原账号；读取实时负载失败时也保持原绑定。原有粘性逃逸关闭开关继续生效。

## OAuth 额度优先与 API Key 自动后备

在本页开启“优先消耗 OAuth 额度，末位 API Key 自动后备”。默认关闭；截止值默认是 **7d 已用 90%**，可设为 1–100。沿用本页分组和模型范围，不需要逐个指定 API Key。

开启后，在当前请求通过准入的同一候选池内：

1. OAuth 必须可调度、最新有效且完整的质量检测轮次通过、质量通过率达标，且没有已知延迟、拥堵、错误或亏损超标。延迟/利润样本不足本身不会阻止已有质量证据的新号参与。质量采用同请求模型的现有历史缓存，通常 30 秒刷新，最多使用 2 分钟内的缓存；最新明确失败取消本策略资格，即使历史平均仍达标。
2. 额度快照必须在 **5 分钟内**，不是未来时间，5h 和 7d 用量有效、重置时间仍在未来；7d 已用严格小于截止值，5h 未耗尽。未知、过期、刚重置但尚未刷新均不压制 API Key，不在请求线程发送探测。
3. 可承接槽位估算为 `ceil(实际并发上限 × 并发占用阈值 / 100) − 当前并发`，再受剩余 RPM 限制，并除以去重绑定分组数向下取整。排队、负载未知和无可用槽位的 OAuth 不提供退让预算。
4. 保持现有风险、容量档、体验档、优先级与加权抽样排序，从 **API Key 子序列的末尾** 逐个转为后备。每个 API Key 的剩余并发槽位消耗等量 OAuth 预算，预算用尽即停止；满载、排队或负载未知的 API Key 不消耗预算。例如 OAuth 共可承接 8 个槽位，末尾 API Key 各余 4 个槽位时，最后两个转后备。账号不能拆分，最后一个账号可能超过剩余预算；这不是吞吐承诺或独占容量预留。
5. 仅将合格 OAuth 移到这些后备 API Key 前面；其他低质量、慢或未知 OAuth 不因此插队。后备列表始终保留，抢槽竞争失败时同次选号即可继续使用 API Key。OAuth 容量减少时自然缩短后备尾部，排名较前的 API Key 先恢复；无合格 OAuth、额度达到截止值或关闭策略时，恢复原算法。OAuth 获得有效的新窗口快照后自动重新参与。

“后备”是一次选号的动态角色，**不写账号 status / schedulable**，不会误开启手动停用账号，也不需要后台恢复任务。新请求与已有允许故障转移的重试会重新计算；不新增已发送请求或已开始流的重试。API Key 在池内仍有排名，恢复时沿用算法顺序，不保存固定名单。

可迁移的 API Key 软会话若按相同策略落入后备，可返回自由选号；硬绑定、previous_response_id 和禁止粘性逃逸继续保留。BPS 优先、订阅优先、compact 能力的现有分池边界仍生效；不同分池的 OAuth 不会压制另一个池的 API Key。若开启独立“订阅优先”，它仍可能在本策略 90% 截止值以外优先使用订阅账号，本策略不会替它解除优先级。

页面增加开关、7d 截止值及“本次选号”角色标记。角色来自最近一次实际构造的调度顺序，是候选身份，**不是实际选中或持续停用记录**；刷新重算分数不会伪造一次新选号。旧配置缺字段默认关闭、阈值 90；旧客户端保存时省略字段会保留服务器当前配置。设置继续存入 `priority_scheduling_v1`，无数据库迁移；关闭开关即可退出本策略，回退旧二进制会忽略新字段。

本策略增加 OAuth 消耗机会，不保证失效前额度耗尽或利润提升。应按同分组、同模型观察 OAuth 消耗占比、失效时剩余额度、API 支出、首 Token 延迟和失败率。

## 账号字段管理

优先调度页面不提供按 Teams、Pro、Plus、API 类别批量生成排序的快捷设置。成本由账号成本倍率参与评分；账号优先级、并发数和负载因子仍可在账号管理中编辑。此前写入的账号字段保留原值；本策略的容量计算始终使用实际并发上限，不再让过大的负载因子掩盖占用。普通调度对负载因子的解释不变。同档需要共同参与分流的账号应设置相同优先级。

## 账号成本倍率

在**账号管理 → 新增 / 编辑账号**的计费字段旁设置“成本倍率”；批量编辑支持勾选后单独设置。默认 `0.1`，允许 `0`，最大 `1000000`。值保存在 `accounts.extra.cost_multiplier`，无需数据库迁移，现有账号未设置时也使用 `0.1`。导入、导出和账号复制随现有 extra 配置保留该值。

- 成本倍率用于优先调度的利润估算，与“账号计费倍率”和“分组计费倍率”独立；成功探测到有效上游 token 倍率后直接更新此字段，包含探测时的峰时倍率。下一次成功探测会再次更新；探测失败、过期或不支持时保留已保存的成本倍率，不恢复默认值。
- 例如成本倍率初始为 `0.1`，上游探测到 `0.14` 后，该字段保存并显示为 `0.14`，基础费用 `100` 的估算成本为 `14`。上游声明的 `0` 允许写入；非法值或超出字段范围的倍率不写入。
- 账号编辑中的“跟随上游”默认开启。关闭后，手填成本不会被后续探测覆盖，上游倍率和余额探测继续正常更新；重新开启后，下一次成功探测更新成本。开关保存在 `accounts.extra.cost_multiplier_auto_sync`，缺省或 `null` 表示开启。
- 充值赠送场景：充值金额能获得 5 倍额度，而上游报告倍率为 `1`，实际成本系数为 `1 ÷ 5 = 0.2`。关闭“跟随上游”，将成本倍率改为 `0.2` 并保存即可；账号列表上游探测列仍显示其报告的 `1.00x`。
- 手工修改成本倍率后立即用于后续评分；跟随开启时，下次成功探测会用上游倍率覆盖。未发生成功探测的账号继续使用手工值或默认 `0.1`。
- 估算成本＝同分组、同请求模型的 `SUM(COALESCE(account_stats_cost,total_cost)) × 当前账号成本倍率`。先聚合未乘倍率的基础费用，只乘一次成本倍率；即使账号计费倍率已是 `0.1`，也不会重复相乘。
- 修改后，在新请求生成候选快照时按当前倍率重估近期利润；历史使用日志、用户扣费和余额不被改写，账单里的历史账号成本列继续按原计费口径展示。
- 成本倍率必须同时保留在完整账号缓存和候选精简快照中，评分读取的是后者。修复旧版候选快照丢失该字段后，升级实例的启动重建会刷新缓存；手工编辑和成功探测也会更新这两份数据。页面“刷新评分”只读取最近一次评分，需有新的自由选号请求才会生成新结果。
- 所有账号统一按此字段估算，不再设置单号采购成本、人民币换算系数、回本窗口或按回本压力插队。旧配置中的 `teams` 对象和 `priority_teams_*` 元数据被忽略，保存新调度配置时不再带上 `teams`。
- 默认 `0.1` 是经营估算值，运营者应按各账号实际成本单独调整，不代表已核实采购价格或汇率。若仍使用独立的分组利润硬门槛，其既有账号计费倍率规则保持不变；本字段作用于本页优先调度评分。

## 数据与排序

1. **质量**：使用对应账号、同一模型的有效质量规则结果。只统计已完整保存的检测轮次；一轮中出现明确错误即失败，全部正确才算通过，网络失败等不确定轮次不计入分母。默认保留 24 小时；停用或修改规则后，旧结果不再参与。
2. **延迟**：默认统计近 60 分钟的流式首 token 延迟 P90，至少 5 个样本（同样作为利润样本下限）。按 `requested_model` 匹配，旧记录回退 `model`。排除缺失/非正首 token 时间及零 token、零费用的失败占位记录；免费但有真实 token 的请求可以参与。非流式总耗时不混作首 token 延迟。
3. **并发**：复用调度器实时并发占用及排队数据。占用达到阈值（默认 80%）或已有排队即标记拥堵。最终仍原子获取并发槽；竞争失败继续尝试后备账号。
4. **利润 / 成本**：按同分组、同模型的使用记录计算，用户扣费为 `SUM(actual_cost)`，估算成本按上节账号成本倍率计算。无首 token 或非流式记录仍参与财务统计。利润＝用户扣费−估算成本，利润率＝利润÷用户扣费；用户扣费为 0 时利润率为空。达到最少样本数后使用历史收益评分，出现亏损降为未达标。OAuth 数据不足时不推断利润；API 可以按独立成本倍率回退估算。不会修改用户扣费，也不保证历史收益等于下一笔收益。

5. **近期错误**：复用账号运行时错误率，超过 20% 降为体验未达标，同时对总分施加错误惩罚。错误 EWMA 除按请求更新外，还以 2 分钟半衰期衰减，避免账号少分到请求后只能靠新成功样本恢复。衰减适用于共用这份运行时统计的普通/优先调度，不改变真实限流、模型冷却或停用截止时间。首 Token 延迟不随空闲时间变小，也不会把空闲计为成功样本。这里不会从“费用为零”推断请求失败率。
   BPS 文本请求及其内联附件在获取托管代理时失败，仍返回原有 503 并记录诊断，但不计入账号错误率，也不作为成功样本消除已有惩罚。实际上游 429、503 及发送后的失败仍按原规则计入。此区分不会立即清空历史错误率或触发额外重试。

先分档再排序：

- 体验达标：有有效质量结果、足够延迟样本、已知负载和财务依据，且质量、延迟、并发均满足目标。
- 数据不足：不存在已知超标，但一项或多项数据缺失。
- 体验未达标：至少一项已知指标超标。

实际选择先区分已知质量不佳、近期错误偏高或历史亏损风险，再按预计占用划分容量档。预计占用取“当前并发加下一次请求”与 RPM 预计占用的较大值，每 10 个百分点一档；缺少负载数据按未知档处理，真实排队排在无排队档之后。容量档相同时，才比较体验档、显式账号优先级和分流权重。因而容量接近时账号优先级有效；存在明显更空闲的安全候选时，较高优先级或略高利润不会持续覆盖容量差异。

例如同一风险档中，43% 占用、66.8 分的账号不会抢在 2% / 0% 占用的两个可用账号前面。全部账号都超过首 Token 目标时，仍区分负载和延迟，不把它们视为相同的“未达标”后仅按收益排序。保留所有后备候选；抢槽失败先尝试其他候选和新鲜负载，穷尽后才建立有界等待。订阅和 compact 能力分池继续生效；关闭跨协议均衡时 BPS 优先规则也继续生效。

对无已知超标、负载已知且低于繁忙阈值、利润与延迟样本都不足的 OAuth 账号，在有达标池时提供 10% 的探索概率；仅允许相同显式账号优先级、容量档不差于首选账号的候选。多个可探索账号共享这部分机会。它不是每 10 次请求必定一次的承诺，也不覆盖真实冷却或权限限制；没有达标池时，数据不足账号直接参与容量分流。

| 策略 | 质量 | 延迟 | 并发余量 | 成本 |
| --- | ---: | ---: | ---: | ---: |
| 体验优先 | 40 | 35 | 20 | 5 |
| 均衡 | 30 | 25 | 25 | 20 |
| 利润优先 | 20 | 15 | 20 | 45 |
| 自定义 | 用户配置 | 用户配置 | 用户配置 | 用户配置 |

各因子取 0–1：质量为通过率，延迟为 `1/(1+P90/目标)`，并发评分为 `(1-当前并发/实际并发上限)/(1+排队数)`（占用比例限制在 0–1）；拥堵分档也使用实际并发上限。财务因子为 `用户扣费/(用户扣费+理论成本)`（盈亏平衡取 0.5、零成本正收入取 1）；API 缺少财务样本时回退 `1/(1+倍率)`。缺失因子取中性值 0.5，OAuth 未知利润不按零收益评分；权重自动按总和归一化，最终乘 `1-近期错误率` 并换算成百分制。

### 分流权重与跨分组竞争

同容量档、同体验档和同优先级内的分流权重为：

```text
可用槽位 = max(0.05, 实际并发上限 - 当前并发) / (1 + 排队数)
评分偏好 = 0.5 + clamp(百分制评分 / 100, 0, 1)
额度偏好 = 0.5 + 0.5 × 有效额度余量
延迟因子 = max(0.02, 1 / (1 + (同模型 P90 / 首 Token 目标)^2))
OAuth 分流权重 = 可用槽位 × 评分偏好 × 额度偏好 × 延迟因子 / max(1, 绑定分组数)
```

延迟样本达到配置下限且 P90 为正时应用延迟因子，否则取 1，不把缺失时间当成零延迟样本。该体验约束在利润优先模式也有效，保留 0.02 下限供恢复及溢出使用。缺少实时负载时可用槽位取 1；满载账号的极小权重仅用于后备/排队顺序，实际抢槽仍跳过已知满载账号。额度偏好复用有效 7d 快照和现有 5h 低余量折扣，数据缺失、过期或窗口重置时取中性值 0.5。API-key 不应用分组数量除数。

绑定分组数由账号全部有效分组 ID 去重计算，不按分组名称、价格推断等级，也不划专属池。一个 OAuth 账号暴露给更多分组时，竞争来源更多；其他条件相同，当前请求更倾向绑定较少分组的账号。多分组账号始终保留正权重，其他候选不可用时仍可使用其容量，不设会造成闲置的固定预留比例。这是容量分配偏好，不是每个分组独享的配额或绝对防挤占保证。

例如四个同档、同优先级、同并发余量的 OAuth 账号分别绑定 5、5、5、2 个组时，权重比为 1:1:1:2.5。绑定两个组的账号期望分到约 45.5%，其余各约 18.2%；实时负载、额度和评分变化会改变比例。抽样按会话/请求锚点生成，不新增共享计数器；使用指数竞争排序，复杂度为 O(n log n)。

## 刷新与回退

配置按实例异步缓存，通常约 5 秒观察到其他实例的配置更新；本实例保存后立即生效。请求线程不执行历史聚合。统计按候选账号集合、分组、模型及窗口缓存，30 秒刷新，最多保留 32 个池、同时进行 2 次后台查询，单次查询限时 2 秒、最多 2000 个候选账号。

冷启动、查询失败、统计超过 1 分钟或超出资源上限时，仍按实时容量分流；不可用的历史信号按未知处理，不恢复旧 Top-K，也不把未知质量当成已验证通过。统计就绪后补入质量、延迟和收益信号。不会因此发送主动探测请求；质量运维可独立补充质量样本。

页面展示当前实例最近一次候选池（最多 100 个账号），包括模型、分组、策略、评分、样本、原因、绑定分组数、分流权重及探索资格。API 增加 selection_policy=capacity_first、capacity_band、bound_groups、selection_weight、exploration_eligible。表格按风险、容量档、体验档、优先级和权重展示，不能把行序理解为最终选中。历史未就绪也展示实时候选。刷新只读快照，不发送模型请求。新页面兼容旧响应缺字段，多实例可能展示不同快照。

## 模型准入与存量账号

均衡不会绕过模型准入。OpenAI OAuth 自动配置为原本没有显式映射的新账号添加别名时，使用 model_mapping_mode=aliases 保留默认模型范围；导入的显式非空白名单继续保留限制。

如果存量号只有一条自动别名而无法入选，应先核实其服务范围，再在账号编辑开启“模型映射仅作为别名，保留默认模型范围”；批量编辑可只修改映射范围，保留各账号不同的别名和凭据，也不会开启 BPS。未标明模式的存量映射继续按旧白名单处理，不根据历史标记猜测并自动扩权。详见 [自动配置](account-auto-config.md)。

分流减少容量侧的集中和等待，不代表上游 P90 必然达到配置的 9 秒等目标；仍需以部署后的同组同模型数据验收。
