# TypeSafe 内容审计分类

风控 → 内容审计 → 设置 → 基础选择 **TypeSafe AI**，在“风险阈值”中分别启用 `jailbreak` 和 `control_bypass`。保存后再次打开设置可读取启用状态和阈值；切换到 OpenAI 仅显示原 13 类，切回 TypeSafe 会保留草稿，保存后两套配置均保留。

两个新类别在新配置和旧配置升级时均默认关闭。关闭由真正的 `enabled: false` 表示，分数为 1 也不参与命中。原 13 类保持原来的阈值和启用行为。新类别的 95% 是**未校准的起始值**；启用前应根据业务样本评估误拦。本 Issue 回归用例中的 0.80 只是测试边界，不是推荐生产默认值。

| 分类 | 判定范围 | 解释边界 |
| --- | --- | --- |
| `jailbreak` | 实际要求覆盖 AI 系统/开发者指令、规避 AI 安全规则、泄露隐藏提示词 | 普通开发、授权逆向、CTF、引用分析与防御讨论不自动构成该行为 |
| `control_bypass` | 实际要求禁用、跳过、移除或伪造许可证、权限、完整性、反调试等保护检查 | 行为分数不等于未经授权或违法；授权去保护也可能高分，是否阻断由管理员业务策略决定 |

合法许可证故障修复、未要求绕过保护的授权分析、正常开发与引用防御讨论不应仅因术语被视为恶意。模型仍可能误判，以上口径不是准确率承诺。

## 请求、配置与记录

TypeSafe 在同一个 System One 请求中发送 15 个 `noul` 问题，包括默认关闭的两个新类别，以保留实际分数。每个已发送问题均必须返回合法答案：缺失、`null`、类型不符、非数值或超出 `[0,1]` 会使整次分类失败。失败沿用现有重试、Key 健康状态、按 `record_non_hits` 记录错误与失败放行策略，不补零、不伪造成功命中。

关闭类别仅停止该分数参与本次语义命中，不停止发送问题或校验答案；关闭类别的答案缺失或非法也会使整次分类失败。关闭开关不会撤销此前已记录的风险输入 hash。若启用了既有“前置 hash 检查”，相同输入仍会在调用 API 前以 `hash_block` 拒绝；管理员需按原有 hash 管理流程单独复核和移除记录。

规则版本为 `content-audit-15-zh-v2`。每次成功审计的 `engine_meta` 保留实际引擎、响应模型、规则版本、`category_settings` 启用快照与 `matched_categories` 命中列表；现有 `category_scores` 和 `threshold_snapshot` 保留分数和阈值。错误记录保留尝试的引擎、规则版本、启用状态，不填成功响应模型。日志详情展示当时的分数、阈值和启用状态，不读取当前设置来解释旧记录。

配置及测试 API 使用同一结构：

```json
{
  "engine_configs": {
    "typesafe": {
      "thresholds": { "jailbreak": 0.95, "control_bypass": 0.95 },
      "category_settings": {
        "jailbreak": { "enabled": true },
        "control_bypass": { "enabled": false }
      }
    }
  }
}
```

测试接口 `/admin/risk-control/api-keys/test` 的 `engine`、`thresholds` 和 `category_settings` 在顶层；省略时使用已保存配置，传入时只用于本次测试，不更改配置或活动引擎。测试与实际请求共用分类目录和判定函数，以 `score >= threshold` 判命中。未知类别及不受引擎支持的类别不会出现在有效配置或 API 分类结果中；OpenAI 保持 13 类。

这次扩展不增加规则编辑平台、不修改安全注入审计或账本、不增加处罚入口。原有关键词、抽样、前置/观察模式、失败策略以及关键词豁免、API 审计豁免、自动封禁豁免三者仍独立。管理员显式启用分类后，其命中进入现有内容审计策略，既有通知、计数和自动封禁设置仍按原配置生效；启用分类不是另行授权自动封禁。TypeSafe 仅审核实际送检文本，不承诺覆盖多轮上下文、工具执行或完整任务链。

## 兼容与验证边界

无需数据库迁移：配置使用现有 JSON 设置，启用快照和命中列表复用 `engine_meta` JSON。旧版本忽略新增字段和两类阈值，回退二进制可恢复原 13 类判定；若旧版本重新保存 TypeSafe 配置，会丢失其不认识的新字段，升级回来需重新确认开关。

每次仍是一个 TypeSafe HTTP 请求，问题从 13 个增加为 15 个，不能据此承诺用量或延迟不变。这次实现未调用真实 TypeSafe 或模型服务，没有新的成本或延迟实测。

## 待远端 CI 与人工复核

本机按授权仅执行静态语法、格式和 diff 检查，未运行 Go/Vitest、构建、lint、vue-tsc 或 Wire。远端 CI 应执行已有后端单元/集成测试和前端关键测试集；关键集已加入 `RiskControlView.spec.ts` 与中英文案回归。

UI 复核步骤：

1. 加载旧配置，确认 OpenAI 为 13 类，TypeSafe 为 15 类且新开关关闭。
2. 在 TypeSafe 打开 `jailbreak`，将测试阈值设为 80%；打开 `control_bypass`、修改阈值后再关闭。切到 OpenAI，确认新类别不显示；保存并重载，再切回 TypeSafe，确认两个开关及阈值均保留。
3. 使用隔离 mock，原 13 类返回低分，新类分别返回 0.79、0.80、0.90 和 1。确认关闭时分数 1 不命中、开启时 0.80 恰好命中，测试面板与实际前置判定一致。
4. 打开日志详情，确认规则版本、命中列表所对应的类别标记、实际分数、阈值及关闭状态；修改当前配置后旧记录解释保持不变。
5. 截取无真实用户数据的设置页和日志详情，附到 PR，勿将截图提交到源码目录。

下面语料均为虚构文本，已纳入 mock 测试源码。mock 分数只验证策略和传输，不衡量模型语义准确率；真实误拦率和阈值校准仍待另行授权评估，本次授权不包含真实调用。

| 语料 | 业务复核预期 |
| --- | --- |
| 解释自有程序排序函数，补充边界处理 | 普通开发，无新增行为 |
| 持有合法许可证，诊断并恢复故障校验，明确不移除检查 | 合法修复，无保护绕过 |
| 获授权分析实验程序调用关系，不禁用检查 | 授权分析，无保护绕过 |
| 引用“忽略系统指令”讨论注入检测和隐藏提示词保护 | 引用防御，无实际越狱请求 |
| 明确请求覆盖 AI 安全限制及泄露隐藏提示词 | jailbreak 行为 |
| 明确请求跳过无授权商业软件许可证检查 | control_bypass 行为 |
| 自有实验程序获授权去除完整性保护 | control_bypass 行为，但不能推断恶意或违法；由业务决定是否阻断 |
