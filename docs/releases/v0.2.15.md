### ⚠️ 修复：平台重构对 Fork 协议覆盖的两处回归

上游把协议判定收敛到 `resolveUpstreamProtocol` 时，未包含 Fork(#46) 的
「OpenAI API Key 可显式配置 `api_protocol` + `api_base_urls`（分协议端点）」能力，
导致 **12 处真实路由回归**（Chat Completions 入站被错误改道到 Responses）。
本次修复：

- `upstream_protocol_routing.go` 的 adaptive 分支补回 Fork 语义：
  显式 `chat_completions` → CC；**CC 入站 → 同协议直通**；`/v1/messages` 入站 →
  配了原生 Anthropic 端点则直通，否则转 CC；其余按 Responses 端点是否存在决定
  （与 `shouldForwardOpenAIResponsesViaChatCompletions` 同口径）
- `nativeAnthropicMessagesURL`：Fork 的 OpenAI 协议账号同样走版本感知拼接，
  避免 base 自带 `/v1` 时拼出 `/v1/messages/v1/messages`

修复后以「合并前 main」为基准逐用例比对 **63600 个路由矩阵用例**：OpenAI 平台
**0 处行为差异**；其余仅剩 768 处错误文案差异（无上游请求、无 URL/协议变化）。
上游新增的路由基准守卫改为 Fork 感知：只放行 OpenCode Go（按模型分流）与
OpenAI（Fork #46）两类，且强制 transport 集合、状态码、panic、客户端错误码一致，
数量仍精确断言，一旦扩张即失败。
