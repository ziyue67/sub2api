# 渠道监控 V3 组件状态页

截图来自本地演示环境：Docker 中的 PostgreSQL 18 / Redis 8、按提交 `2057cdc12` 构建的后端、前端开发服务器、仅监听本机的假上游，以及无头 Chromium（CDP）。分组名、倍率、账号、用户和请求全部是虚构数据；没有连接生产数据库，也没有向真实上游发出模型请求。截图时间为 2026-10-05 02:05 前后（北京时间）。

V3 是新增的展示模式，没有修改前对照；V1、V2 页面不变。

## 数据怎么来的

- 2026-09-27 起 7 天的请求记录由脚本合成后写入 `usage_logs`（成功）和 `ops_error_logs`（失败），再用 V2 聚合器同一段 SQL（`RecomputeRange`）一次算出一分钟统计和小时汇总。
- 2026-10-04 20:52 起，演示用户的 13 个 API Key 持续经本机网关真实发请求（白天多、夜里少），统计由运行中的 V2 聚合器每分钟更新。假上游按分组返回：基本正常、经常变慢（首 Token 10.5–12.5 秒）、一直 502、或每 30 分钟中断 10 分钟。
- 演示配置：每格 5 分钟、90 格、近 7 天可用率、红色失败率 ≥ 20%、黄色失败率 ≥ 5% 或首 Token 中位数超过 10 秒、每格至少 3 个请求，不计入失败的错误类型为默认值。

## 验收要点

- 置顶卡片显示组件名、倍率、近 7 天可用率、最新状态和 90 格状态条；分类两列排列，最后一行只剩一个分类时占满整行。
- 所有组件的格子在时间上对齐；正在统计的最新一格请求数不够时显示为闪动的「统计中」，不显示为灰色。
- 一直报错的三个分组各只有一条「进行中」事件，夜里请求稀少时出现的个别灰格没有把一次故障拆成多条；Gemini 每 30 分钟一次的 10 分钟中断各记一条。
- 普通用户的页面和接口里没有请求数；管理员预览的置顶卡片显示「33642 次请求」。
- 1440 和 390 宽度下 `document.documentElement.scrollWidth` 都等于视口宽度，没有横向溢出。
