# 托管 OpenAI 账号的 2FA 更换与导出

凭证运营账号行的「2FA 管理」支持手动更换 TOTP，以及导出密钥、验证器二维码、JSON 和 `邮箱----密码----2FA密钥`。只允许管理员操作，观察者不可读取。此功能管理上游 OpenAI 账号，与 Sub2API 用户自己的两步验证无关。

实现位于本仓库的 `tools/openai_totp_rotation.py`，直接请求 OpenAI 网页 MFA 接口。登录复用既有运行包中的固定 toSub2 登录程序，没有引入 GPTServiceLite 服务或其代码依赖。更换任务始终由本地 Worker 执行，与 Session Studio 重登设置无关，使用账号配置的登录出口。

## 使用

1. 在凭证运营保存账号的正确邮箱、密码、当前 TOTP 密钥，并启用凭据加密。邮箱必须与托管账号的身份一致。
2. 打开「2FA 管理」，点击「更换 2FA」并确认。新版本 Worker 及可写的持久恢复目录必须已经就绪。
3. 系统完成登录，申请并保存新密钥，然后激活。使用新密钥在全新会话中登录，并在新的 TOTP 时间窗口验证旧密钥被明确拒绝后，才更新自动重登配置并报告成功。
4. 通过「显示并导出凭据」获取新密钥或二维码。默认不包含密码；选择「包含登录密码」后可下载完整三字段文本。密码包含 `----` 或换行时使用 JSON，以免导入时损坏字段。

服务端返回的密钥决定新的绑定，界面不会让管理员随意填一个本地密钥冒充已完成上游修改。仅更换 2FA 不会自动注销已有会话，也不会更换账号密码。

## 新凭据的保存顺序

```text
旧凭据加密写入本地恢复日志
→ 使用旧凭据登录并检查账号身份
→ 持久记录 enrolling 阶段
→ 向 OpenAI 申请新密钥
→ 本地 AES-256-GCM 加密保存新密钥及绑定 session_id，fsync 文件和目录
→ API 加密保存候选密钥，PostgreSQL synchronous_commit=on 提交并确认
→ 持久记录 activating 阶段
→ 提交激活（无自动重试）
→ 新会话验证新密钥可用、旧密钥被拒绝
→ 事务内更新有效 TOTP 和任务结果
```

两份新密钥都保存成功之前，不发送激活请求。保存失败、ACK 丢失、激活超时或验证失败不会重新申请密钥。密钥不放在普通日志、命令参数、状态接口或审计正文；下载响应使用 `Cache-Control: no-store`。关闭弹窗会清除组件中的明文和二维码，迟到的请求结果不会重新显示。

数据库任务保留加密的原密钥、密码快照和候选密钥。本地恢复日志保存同样的凭据以及 enrollment session_id，并且不自动清理。保留旧凭据便于诊断和恢复，不代表旧密钥在上游仍然有效。

## 中断和恢复

- 激活结果不确定时显示「待确认」。同账号的重新更换、普通重登及登录配置编辑被阻止，避免覆盖或重复更换。
- Worker 消失后，15 分钟未推进的任务转为待确认。状态查询也执行这项检查，即使所有 Worker 都离线，管理员仍可导出已入库的恢复凭据。
- 「验证新密钥」只验证已保存的新密钥，不执行 enroll/activate；成功后采用新密钥。
- 「验证原密钥」要求原密钥可以登录，且已知候选密钥被明确拒绝；成功后继续使用原密钥。没有收到候选密钥的任务则只检查原密钥是否还能完成 MFA 登录。
- 网络错误、风控响应或未进入 MFA 都不能当作“旧密钥已经失效”的证据；这些结果保持待确认。
- 本地已经持久保存、但 API 尚未确认的候选密钥会在 Worker 后续轮询中补存。补存不能覆盖数据库已有的不同候选，也不能重开已结束的任务。
- 已保存的新密钥不能被下一次尝试覆盖。同账号的任务互斥由数据库约束保证；配置更新还检查版本，拒绝更换前读取的旧配置在更换后覆盖新值。

OpenAI MFA 是非公开网页协议。本地故障处理不能保证上游永远维持既有 enrollment/activation 语义：申请请求已经到达但响应完全丢失时，客户端无法恢复从未收到的密钥。这种情况保持待确认，尝试验证原密钥，不自动重新 enroll。上线验收须使用隔离账号核实当前接口行为，不能把 mock 测试当作真实账号安全保证。

## 运行包及备份

内置 Worker 自动使用应用持久数据目录下的 `credential-worker/totp-recovery`，不放在某个版本的临时解压目录。独立 Worker 需设置绝对路径：

```ini
OPENAI_TOTP_JOURNAL_DIR=/var/lib/sub2api-reauth/totp-recovery
```

目录必须为 Worker 可写的持久存储，权限 `0700`。加密 key 和记录权限为 `0600`。容器运行时将该目录挂载到持久卷；不要使用随容器重建丢失的可写层。未配置或不能安全写入时，Worker 不领取 2FA 任务；旧版 Worker 不会误领此任务。

备份必须一起保留数据库、凭证运营原有加密 key，以及整个 `totp-recovery` 目录（包含 `key.bin` 和 `.sealed` 文件）。丢失恢复 key 时不会生成新 key 覆盖旧档案。恢复档案不应加入 Git、普通日志或公开备份。

迁移 `269_openai_totp_rotation.sql` 新建状态表和配置保护触发器，复用重登任务的活跃账号唯一约束。发布时 API、前端和 Worker 运行包一起更新。回退二进制前处理未完成任务；回退不会撤销上游已经更换的 2FA，也不能通过把数据库改回旧密钥完成上游回滚。

## 离线验证

- Python 故障注入覆盖本地写盘失败、数据库 ACK 丢失、激活超时、恢复仅验证和日志脱敏。
- Node 验证加密档案可重读、文件权限、候选不可覆盖、密钥丢失拒绝重建、密文篡改拒绝解密。
- Go 服务/路由验证管理员边界、导出来源、加密先于保存、Worker 能力检查。
- PostgreSQL 集成验证任务并发互斥、过期 Worker 隔离、原子切换、旧配置写回拒绝和候选恢复。
- Vue 测试覆盖显式导出、默认不带密码、待确认禁止重新更换、关闭后忽略迟到的明文响应。

开发测试使用虚构账号和本地 mock，不修改真实账号。
